# Feature parity ledger

The target is the upstream feature set, not just similar-looking controls. Unchecked items are not implemented or not verified; an RPC-accessible operation is not automatically a native UI equivalent.

## Agents and context

- [x] Native Anthropic/OpenAI-compatible agent loop; MCP, Lua extensions, skills, memory, compaction.
- [x] Snap compaction (omp's `snapcompact`): `/compact snap` or `compaction = "snap"` archives older native history as 8x10-cell pixel-font PNG frames (1072 px for Anthropic, 768 px for first-party OpenAI) without a model call, keeps ~30k characters of recent turns verbatim, persists frames in the session and re-archives from the stored source so frames never nest. A tail is always kept (cut before an assistant message in one long turn), the latest user request is carried verbatim, tool outputs shrink before any history is dropped (dropped user prompts are quoted in the legend), and a mostly non-ASCII history is summarized instead of snapped. Unit and integration tests; a frame was read back by a GPT vision model (`codex exec -i`), which returned the exact number and file path planted in it and the first code lines. Not verified: Claude reading the frames, billed-token savings versus a text summary, frame-size tuning. Limits: ASCII only in the grid (other text such as Japanese is listed as plain text beside the frames), non-vision providers fall back to the summary.
- [x] Native sub-agent orchestration (omp's `task`): `tasks[]` run in parallel (4 at a time) with shared `context`; bundled `task`/`scout`/`reviewer` plus custom agents from `.greencode/agents/*.md` and `.claude/agents/*.md` (tool allowlist enforced, not just advertised); `isolated` git worktrees whose changes are retained; `background` jobs delivered as later messages and aborted on cancel; sub-agents may nest one level (depth 2, a grandchild cannot spawn). ## Token efficiency

- [x] Pi/OMP own their prompts, tools, history, extensions and compaction. GreenCode does not prepend its own system prompt, tool schemas or UI transcript.
- [x] Direct Pi versus GreenCode/Pi comparison on a deterministic local HTTP server: two model requests each, identical model/messages/tools fields, zero added prompt bytes. Includes a real Pi `read` tool round trip. Run `python3 scripts/check_pi_parity.py` after building the CLI.
- [x] Direct OMP versus GreenCode/OMP: same two-request read/denial check, zero wrapper prompt bytes ([report](benchmarks/omp-wrapper-2026-11-12.json)). This run explicitly limited OMP to four tools and disabled LSP; it does not measure the full default OMP surface.
- [x] Native prompt budget: the system prompt (418 B) plus 12 tool schemas (3,941 B) is 4,359 B, below the Pi baseline of 5,563 B; `native_prompt_stays_lean` caps it at 7,000 B so new tools cannot silently inflate every request.
- [x] DeepSeek optimizations: output budget clamped to 8,192 tokens, `prompt_cache_hit_tokens` counted as cache reads, `reasoning_content` kept as a thinking block, and compaction triggered at 60k tokens instead of the 150k default. Parsing is unit-tested; no live DeepSeek request was made.
- [x] Same-task prompt size, local model: the native loop sent ~1,643 prompt tokens for a read-tool task versus ~7,988 for the OMP engine (≈4.9×), both completing the task ([report](benchmarks/native-vs-omp-local-2026-11-13.json)). The native prompt is also below the 5,563-byte Pi baseline.
- [ ] OMP engine as lean as Pi: not established. Measured on gpt-6-luna (`scripts/benchmark_tasks.py`, 4 tasks x 3 runs, every OMP model role pinned to luna; `docs/benchmarks/tasks-2026-11-13.json`): total input OMP default 1,002,302 vs Pi 101,991 tokens (9.8x), OMP lean flags 370,494 (3.6x); uncached input 192,318 / 124,094 vs Pi 52,967; median first-request input 7,955 / 4,289 vs Pi 1,178. OMP stays heavier than Pi even stripped to four tools, and no feature stripping is applied to normal OMP sessions to inflate this result.
- [x] GPT-6 Luna live cache smoke test: five verified lookup turns, one read; token-weighted follow-up hit rate 96.15% (all requests 74.90%). See [measurements and limits](cache-efficiency.md); not a coding-quality comparison.
- [x] Same-model real-task quality and billed-token benchmark against Pi: gpt-6-luna, 4 deterministic tasks (bugfix/feature/refactor/lookup) x 3 runs per harness, report `docs/benchmarks/tasks-2026-11-13.json` (2026-11-13 rerun, every OMP role pinned to luna). Passed: Pi 12/12, OMP default 12/12, OMP lean 12/12, native 11/12, OMP+advisor 11/12. Total input: Pi 101,991, native 124,098, OMP lean 370,494, OMP+advisor 403,091 (+67,989 advisor input), OMP default 1,002,302. The native miss is a refactor run that reported success without editing any file; the advisor miss is a lookup run that answered `27502750`. Small N, one model, one date; it does not show equal quality on harder tasks or the subscription's real cache behaviour beyond reported `cache_read`.
- [x] Native GreenCode versus Pi harness quality/token benchmark: after the tool-output caps, trimmed schemas, codex cache key and early-answer prompt, two final-code paired runs passed 24/24 on both harnesses with native at 210,080 input tokens vs Pi 223,850 (0.94x; 0.84x and 1.04x individually, median first request ~1,170 vs ~1,179). Eight paired runs on the same day put native between 0.83x and 1.29x of Pi (native lower in 4 of 8 runs, 891,789 vs 874,791 summed = 1.02x; pass rate 95/96 vs 95/96), i.e. parity on average with run-to-run variance, not strictly below Pi every time (caps8-12 ran earlier variants of the prompt/caps). Reports: `docs/benchmarks/tasks-2026-11-13-caps8.json` .. `-caps15.json` and the table in `docs/cache-efficiency.md`. Small N, one model, four synthetic tasks.
- [ ] OMP's optional advisor/subagents/memory/voice features under a common token budget. Enabling extra model work can cost more than minimal Pi. Only the advisor was measured (`docs/benchmarks/tasks-2026-11-13.json`): its turns are billed separately and are absent from the CLI usage events, so they were summed from the 12 `__advisor.jsonl` transcripts (67,989 input tokens, 1,665 output) on top of 403,091 primary input for the same lean flags without it, which spent 370,494. It passed 11/12: one lookup run answered `27502750` (the value twice). Subagents, memory and voice were not benchmarked.

## OMP execution features

The `omp` backend uses the installed OMP engine. The native TUI uses GreenCode's Rust engine and TOML, not OMP RPC. OMP file imports are explicit and limited to the mappings below.

- [x] The `omp` backend runs the installed engine unchanged, so its hashline/AST edits, persistent bash and eval, LSP/DAP, typed subagents and Agent Hub, TTSR rules, memory backends, MCP and extension management, browser/computer, review/annotate and collaboration features are available through it (v18.19.0 exposes `--tools`, `--no-lsp`, `--advisor`, `--restore` for subagents, and the engine contains the hashline, ast_grep, lsp, dap, subagent, advisor, memory and mcp tooling).
- [x] Native `computer` uses window-addressed background pointer input for coordinate clicks, drags and wheel events, in addition to accessibility actions. Verified on macOS with an inactive AppKit test window: screenshot coordinates reached a custom canvas, double/right clicks, drag and scroll arrived, out-of-window input was rejected, and `super+a` plus Unicode typing replaced text without activating the target. SkyLight availability and app acceptance vary; full Codex parity across app frameworks is not verified.
- [x] Native LSP queries use one server process per project root and language server (reused across calls), a 20 s request timeout, and wait for the server's work-done progress before the first query; every action re-syncs the file (didOpen/didChange) so an edited file is never answered from a stale overlay. Supports rust-analyzer, gopls, typescript-language-server and pyright-langserver; only rust-analyzer is exercised by the integration tests (definition, missing server, open→edit→query resync). Actions: diagnostics, definition, references, hover, workspace symbols. Diagnostics report an explicit unknown state (server silent or exited) instead of claiming a clean file, and re-check after didSave.
- [x] Native terminal UI: default for interactive native threads; model/thinking/permission pickers, multiline input, slash completion, streaming, tool approval and questions, queued follow-ups, steering, interruption, and saved-session selection. `--text`, `-p`, and `--json` keep the CLI path.
- [x] Native configuration CLI: `config path/list/get/set/reset`, explicit TOML overlays, tool/context toggles and system prompt flags, terminal display/follow-up settings, and `[task]` concurrency/depth/runtime/model/result/isolation/background settings.
- [x] Native local HTML transcript export (`/export`, `--export-html`); no upload or overwrite. The native TUI aligns model-picker and plan-toggle shortcut aliases with OMP.
- [x] Native TUI configuration for automatic resume (latest modified thread in the current directory), completion count, OSC terminal progress, and foreground colors from explicitly selected OMP theme JSON.
- [x] OMP-format keymaps for native model selection/cycling, plan, thinking, thread prompt history, queue/dequeue, tool display, external editor, and character/word/line movement and deletion. Keymap files layer explicitly, last per action wins. `/hotkeys` reflects remaps. Picker and approval keys remain native.
- [x] `config import-omp FILE [FILE...]` converts supported explicit YAML settings to a TOML overlay on stdout. Base and profile can be layered without writing the global config or copying credentials.
- [x] Native TUI can expand retained tool results and toggle tool activity or thinking visibility without rerunning; errors remain visible. Tight layout and OMP selection, user, tool and status backgrounds are supported.
- [x] Native TUI `/settings` edits terminal preferences in place, using the same global TOML editor as the CLI. In launches with an explicit overlay, edits are process-local.
- [x] `config import-omp --profile NAME` resolves an explicitly selected OMP profile and emits supported settings and inherited keymap paths. Native startup does not auto-select OMP profiles.
- [x] Native TUI draft editing via `$VISUAL` / `$EDITOR` (`Ctrl+G` by default). The edited text returns to the composer without sending; a failed editor preserves the original draft.
- [x] Native TUI `/review` selects tracked staged/unstaged changes, a merge-base diff, or a recent commit. Explicit GitHub PR and GitLab.com MR targets use local `gh`/`glab` authentication; the remote review disables tools and local image attachments. Reviews run in plan mode; `/plan` restores the prior mode. Untracked files and inline annotation are not supported.
- [x] Native TUI can display successful turns' primary model token totals and prompt-to-yield time; these rows are not persisted. OMP `display.showTokenUsage` and `display.showTurnTime` map to the native settings.
- [x] OMP `contextFiles.extra`, `task.perCallModelAllow`, and `task.agentModelOverrides` are imported. Extra instruction files are read only from the native thread's working directory; OMP's ancestor, primary checkout, and user-scope discovery are not imported.
- [x] Native TUI recovers drafts cleared with `Ctrl+C` through chronological `Up`/`Down` recall, without storing them or exposing them in search. `composer.recallClearedDrafts` maps to the native setting.
- [x] OMP `compaction.midTurnEnabled` and `compaction.thresholdTokens` map to native controls. Disabling mid-turn compaction retains the tool result for the next model request and still allows compaction before the next user turn. Subagents continue to compact mid-turn.
- [x] Native fixed compaction thresholds by exact model or longest matching model prefix. OMP imports `compaction.modelThresholdsEnabled`, fixed `fN` entries, and per-entry resets. Percentage thresholds, numeric base windows, and extended-context tier selection are not native equivalents.
- [x] Structural read summaries (`read.summarize.*`): `read` without `offset`/`limit` returns folded bodies instead of the first 400 lines. A character-level scan folds brace/bracket bodies and block comments (Python by indentation, Markdown/text paragraphs when `prose` is on), merges a body into `head … tail`, then BFS-unfolds spans up to `unfoldUntil` visible lines without passing `unfoldLimit`; the footer names the hidden range so a selector read or edit can follow. Files under `minTotalLines`, unknown extensions and 2 MB+ files stay verbatim; summaries record only shown lines for `edit.enforceSeenLines`. Unit tests on Rust/Python/Markdown fixtures; not a tree-sitter parse, so a multiline string literal is never folded.
- [x] Native speech output (`speech.*`, `tts.*`): `speech.enabled` speaks streamed output in the native TUI sentence by sentence, `speech.mode` selects all/assistant/yield, `speech.enhanced` rewrites the turn's text with the tiny/smol role before one final utterance and falls back to mechanical cleanup, and both rates clamp to 0.8–1.3. Phonon voice ids map to macOS `say` voices. `speechgen.enabled` toggles the `tts` ext tool, which writes .wav/.aiff/.m4a/.caf on-device and other formats through xAI Grok Voice (a clear error when neither is available). The GUI's speak action shares the same core selection. Unit tests cover mode selection, rate clamping, markdown→prose, voice mapping and both TTS backends (a local HTTP mock for xAI); no audio output was heard on this machine.
- [x] Native `live.*`: `greencode-cli live [TEXT] [--out FILE]` opens an OpenAI Realtime-compatible WebSocket, sends `session.update` with `live.voice`, sends `conversation.item.create` + `response.create`, and prints the transcript (PCM deltas are written as WAV with `--out`). `live.endpoint` accepts http(s)/ws(s) and derives `/realtime?intent=conversation&model=…`; empty uses the Codex backend with the signed-in token. `live.apiKey` resolves a literal, an environment variable name, or `!command`, and is only sent to the configured endpoint. Handshake and server-error paths are covered against a local WebSocket mock.
- [x] Native tiny models (`providers.tinyModel*` → `tiny_model.device|dtype`): `tiny/<repo>` and `local/<repo>` model specs run through mlx-lm (`mlx`/`metal`) or an embedded ONNX runner (`onnxruntime` + `transformers`), used by whichever text generation path selects such a model (titles, memory, `speech.enhanced`). `GREENCODE_TINY_DEVICE`/`GREENCODE_TINY_DTYPE` override the config; unknown device/dtype values are rejected at config load and a missing runtime names the install command. Backend selection and spec parsing are unit-tested; no model weights were downloaded here.
- [ ] OMP-only services and accounts, and subsystems native lacks (status line, inline images, mouse, hyperlinks, branch sessions, prewalk, speculative launch, completion probe, clone backends, fetch backends, model presets).

The native harness deliberately does not clone OMP's TypeScript plugin runtime, terminal collaboration,
or inline annotations. The YAML importer is an allowlist, not a general OMP configuration loader:
there is no automatic project/profile discovery, provider or credential import, percentage compaction,
extended-context tier selection, or full theme/keymap compatibility. Native TOML and the documented
mappings above are the supported surface. Use OMP itself for workflows that require the original behavior.
